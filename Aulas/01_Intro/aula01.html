Aula 01: Separation of Concerns(Soc)

Separar um sistema em partes, onde cada parte trata de uma responsabilidade específica. Uma responsabilidade = uma preocupação (concern) que pode evoluir ou mudar independentemente. O objetivo não é criar mais elementos: é reduzir dependências desnecessárias.

Soc em diferentes niveis

  • Arquitetura → Separa grandes responsabilidades do sistema
  • Camadas → Separa apresentação, aplicação, domínio e infraestrutura
  • Módulos → Agrupa funcionalidades relacionadas
  • Classes/funções → Cada unidade tem uma responsabilidade clara
  • Código → Evita misturar lógica, acesso a dados e apresentação

Arquitetura em Camadas

  1. Presentation / UI: Recebe pedidos e apresenta resultados
  2. Application / Services: Coordena casos de uso
  3. Domain / Business: Regras e conceitos do negócio
  4. Infrastructure / Data: Base de dados, APIs, ficheiros, serviços externos

Beneficios

  • Manutenção mais fácil
  • Testes mais simples
  • Menor impacto das mudanças
  • Código mais reutilizável
  • Equipas podem trabalhar em partes diferentes
  • Mais fácil substituir tecnologias
  • Problemas são mais fáceis de localizar

Concluindo

Separation of Concerns é uma forma de controlar complexidade. Aplica-se à arquitetura, aos modelos, aos módulos, às classes e às funções. Boa separação cria componentes coesos e pouco acoplados.

A melhor arquitetura não é a que tem mais camadas — é a que torna as mudanças mais previsíveis.
